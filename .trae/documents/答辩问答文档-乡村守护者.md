# 乡村守护者智慧养老平台 — 答辩问答文档

> 本文档对照公车审批系统问答格式编写，覆盖十大类共 35 道常见答辩问题

# 一、项目背景与业务价值类

**1. 为什么要开发"乡村守护者"这个智慧养老平台？它解决了什么痛点？**

**参考答案**：我国农村空巢老人比例已超过 60%，传统养老模式面临三大核心痛点：

- **安全监护缺失**：老人独居在家，突发疾病、跌倒、走失时无人知晓，往往错过最佳救助时间。传统手环设备大多面向城市用户，缺少针对农村场景的防摔、SOS 等核心功能。
- **服务资源分散**：村级卫生所、乡镇服务商、民政部门之间的信息相互割裂，老人有服务需求时找不到渠道，服务商有资源时又找不到老人。
- **监管手段落后**：政府只能靠人工报表了解养老工作进展，无法实时掌握辖区老人的健康状态、服务覆盖率和预警处理情况。

本系统构建了"**智能手环感知 → 村级专员响应 → 服务商上门 → 政府实时监管**"的四级联动闭环，实现了事前可预防（健康监测）、事中可求助（SOS/跌倒告警）、事后可追溯（工单流转），真正让农村老人享受到智慧养老的红利。

**2. 系统的核心受众是谁？主要应用场景有哪些？**

**参考答案**：核心受众分为五类：

| 角色 | 核心需求 | 典型场景 |
|------|---------|---------|
| **老人**（ELDERLY） | 安全监护、一键求助、服务预约 | 手环监测体征、跌倒自动报警、SOS 紧急求助、预约上门服务 |
| **家属**（FAMILY_MEMBER） | 远程关爱、健康追踪 | 实时查看老人心率/血氧、接收预警通知、为老人预约服务 |
| **村级专员**（VILLAGE_STAFF） | 辖区内老人管理、预警处理 | 查看本村老人健康大盘、处理预警工单、审批服务预约 |
| **服务商**（PROVIDER） | 工单接单、服务交付 | 接收派单、上门服务、记录服务结果、提交评价 |
| **政府管理员**（GOV_ADMIN） | 全域监管、数据分析 | 区域数据总览、服务商资质审核、设备监控、数据大屏 |

**3. 为什么选择自主研发，而不是采购第三方养老平台？**

**参考答案**：调研发现，市面上的养老平台存在三个不适合农村场景的问题：一是**成本高**，按年收费动辄数十万，村级财政难以承受；二是**功能错配**，大多数平台面向城市高端养老社区，缺乏农村特色的防摔手环、语音方言识别等需求；三是**数据孤岛**，第三方平台的数据无法与政府现有的民政系统打通。

自主研发的好处：一是**成本可控**，一套后端服务可同时支持 Web 管理端和移动端小程序，一次投入长期使用；二是**可定制性强**，从硬件手环（ESP32）到后端服务再到前端展示全栈自研，任何环节都能按需调整；三是**数据自主可控**，老人健康数据存储在自己的数据库，符合数据安全要求。

# 二、技术架构与平台能力类

**1. 整体技术架构是如何设计的？为什么做这样的技术选型？**

**参考答案**：系统采用**前后端分离 + IoT 设备接入**的三层架构：

- **感知层**：基于 ESP32 的自研智能手环，集成 MAX30102（心率血氧）、ADXL345（跌倒检测）、SFD01（毫米波雷达）、GPS 定位等传感器，通过串口/MQTT 双通道上传数据。
- **平台层**：Node.js + Express 后端，MySQL 数据库，自建 MQTT Broker 接收设备数据，Device Engine 引擎实现告警规则评估和设备状态管理。
- **应用层**：Vue 3 + Element Plus Web 管理端（面向政府/村级/服务商），uni-app 移动端（面向老人/家属）。

**技术选型理由**：
| 选型 | 理由 |
|------|------|
| Node.js + Express | 高并发 IoT 数据处理的 I/O 密集型场景，Node.js 事件循环天然适配 |
| Vue 3 + Composition API | 响应式数据流更适合实时体征数据展示，组合式 API 比选项式 API 代码复用度更高 |
| MySQL | 关系型数据（老人/设备/工单/审批）需事务一致性，MySQL 比 NoSQL 更适合此类 OLTP 场景 |
| MQTT（Aedes）| IoT 数据上报场景的标准协议，比 HTTP 轮询更节省带宽和电量，支持 QoS 保证送达 |
| ESP32 | 成本极低（约 30 元/片），支持 WiFi/蓝牙/串口多种通信方式，开箱即用的 Arduino 生态 |

**2. 数据库为什么同时兼容 MySQL 和 SQLite？**

**参考答案**：这是一个很实际的技术决策。项目初期开发时，团队成员在自己的电脑上用 SQLite 跑得非常顺畅，因为 SQLite 是文件数据库，零配置、无需安装。但部署到政府服务器时，对方要求必须用 MySQL。如果全量修改代码中的 SQL 语句，工作量巨大且容易引入 bug。

我们的解决方案是实现了一个**SQL 语法兼容层**（[config/db.js](file:///c:/Users/50453/Desktop/rural-guardian/rural-guardian/backend/config/db.js)），它运行时自动将 SQLite 方言（如 `datetime('now','localtime')`、`ON CONFLICT`、`strftime`）逐一替换为 MySQL 对应的语法（`NOW()`、`ON DUPLICATE KEY UPDATE`、`DATE_FORMAT`）。这样代码中用 SQLite 语法编写，部署到 MySQL 环境时无缝切换，一行代码不用改。

**3. 复杂的工作流是如何设计的（预警流转 + 工单审批）？**

**参考答案**：我们实现了**三级告警升级流转**和**多角色服务工单审批**两套流程引擎。

**预警流转**（[alert-flow.js](file:///c:/Users/50453/Desktop/rural-guardian/rural-guardian/backend/routes/alert-flow.js)）：
- 设备上报异常数据 → 引擎自动创建 `CRITICAL/HIGH/MEDIUM` 告警
- 村级专员收到通知 → 必须在 2 小时内确认处理 → 超时自动升级到乡镇管理员
- 家属同步收到推送 → 确认老人安全后可关闭告警
- 全部处理完成后自动归档，形成完整的"发现-响应-关闭"留痕记录

**服务工单审批**（[order-flow.js](file:///c:/Users/50453/Desktop/rural-guardian/rural-guardian/backend/routes/order-flow.js)）：
- 老人/家属提交服务预约 → 村级专员初审确认需求
- 政府管理员审批（涉及补贴的服务）→ 审核通过后自动派单给服务商
- 服务商接单 → 上门服务 → 提交服务完成记录
- 老人/家属评价 → 村级专员复核 → 订单完结

每个步骤的操作人、操作时间、从状态到状态都在 `_flow` 表中全程留痕，方便事后审计。

**4. 系统如何与其他外部服务集成？**

**参考答案**：系统采用**可插拔的服务集成架构**，通过统一的 `service_call_log` 表记录每次外部服务调用。目前集成了以下服务：

| 服务 | 用途 | 集成方式 |
|------|------|---------|
| **智谱 GLM**（AI）| 老人健康数据分析、智能问答 | REST API + Token 计量 |
| **科大讯飞**（语音）| 方言语音识别、语音合成播报 | REST API + SDK |
| **高德地图**（GIS）| 老人位置展示、电子围栏、服务商导航 | JavaScript API + WebSocket |
| **阿里云短信** | 预警短信通知、短信验证码登录 | REST API |
| **极光推送**（JPush）| APP 推送通知（预警/SOS/工单状态变更）| REST API |

集成设计的关键是**服务调用审计**——每次外部 API 调用都记录 `service_call_log`，包括耗时、状态和消耗的 Token 数量，便于成本核算和服务质量监控。

# 三、功能实现与测试验证类

**1. 如何防止设备数据冲突（同一老人多个设备数据冲突，或多个老人共用同一设备）？**

**参考答案**：我们设计了**设备-老人一对多绑定机制**：

- 每个老人可以绑定多个设备（手环 + 固定雷达），设备引擎会按 `device_id` 存储实时数据到 `device_realtime` 表，互不干扰。
- 前端展示时，按 `elderly_id` 聚合查询最新数据，取 `last_report_at` 最新的设备数据展示。
- 一个设备只能绑定一个老人，通过 `device_binding_approval` 审批流程控制绑定关系，避免多个老人共用设备导致数据混乱。

**2. 实时体征数据是如何从硬件流转到前端的？延迟多少？**

**参考答案**：完整数据链路如下：

```
ESP32 手环传感器采集
      ↓ (串口 115200bps)
串口桥 serial-bridge.js → 解析 JSON/日志 → MQTT publish
      ↓ (MQTT QoS 1)
本地 MQTT Broker (1883端口)
      ↓ (事件回调)
Device Engine 解析处理 → 内存缓存更新 → UPSERT 数据库
      ↓ (5 秒 HTTP 轮询)
前端设备监控页 → GET /api/device-monitor/realtime
```

**端到端延迟**：传感器采集 → 串口传输（< 100ms）→ MQTT 发布（< 50ms）→ 引擎处理（< 10ms）→ 数据库写入（< 30ms）→ 前端轮询（最大 5s）。整体延迟平均 **3~5 秒**，满足养老监护的实时性要求。

如果未来需要更低延迟，可以将前端轮询改为 MQTT over WebSocket 直接订阅设备数据主题，延迟可压缩到 < 500ms。

**3. 如何进行告警规则的引擎设计和防误报处理？**

**参考答案**：告警规则引擎实现了三层防误报机制：

- **第一层 — 零值过滤**：传感器未佩戴或初始化未完成时，引擎自动跳过零值数据，不触发告警。只有连续上报 3 个有效数据后才开始评估规则。
- **第二层 — 重复告警抑制**：同一设备同一指标在 1 分钟内不重复创建告警。比如心率 > 120 持续 5 分钟，只产生 1 条告警记录，减少冗余通知。
- **第三层 — 阈值渐变**：告警阈值分为"警告"和"严重"两级。例如心率 > 100 触发 WARN 级别 → 仅通知家属；心率 > 130 且持续 30 秒以上才触发 CRITICAL → 同时通知村级专员和家属。

此外，跌倒检测使用**多传感器融合**策略：只有当 ADXL345 加速度计检测到撞击 + SFD01 毫米波雷达检测到人体跌倒姿态 + 连续 10 秒无站立信号时，才判定为跌倒，极大降低了误报率。

**4. 移动端体验是如何做适老化设计的？**

**参考答案**：老人端 APP 做了专门的适老化设计：

- **超大字体**：最小字号 28rpx（约 14px），正文字号 32rpx，标题字号 44rpx，是常规 APP 的 1.5 倍
- **高对比度色彩**：按钮使用深青色 `#0d9488` + 白色文字，SOS 按钮使用大红色 `#ef4444`，确保色弱用户也能看清
- **SOS 长按防误触**：紧急求助按钮需要**长按 3 秒**才触发，期间可随时松手取消，避免老人误触导致虚假报警
- **多模态交互**：支持语音呼叫客服（搭载科大讯飞方言识别，广东话/四川话等均可识别）、NFC 刷卡识别身份（老人卡贴近手机自动登录）
- **自动轮播体征数据**：首页体征卡片自动 5 秒轮播心率/血氧/体温/步数，不用手动滑动就能看到所有数据

# 四、个人贡献与团队协作类

**1. 你在项目中具体负责了哪些模块？遇到了什么难点？**

**参考答案**：我主要负责以下模块：

- **IoT 设备数据链路**：从 ESP32 手环串口数据采集、JSON 解析，到 MQTT 消息发布、Device Engine 引擎处理，最后到前端设备监控页面展示的完整链路打通
- **设备实时监控与告警规则引擎**：实现设备实时数据缓存、告警阈值评估、跌倒/SOS 事件处理、电子围栏检测
- **设备监控大屏页面**：基于 Vue 3 + ECharts 开发的实时设备监控界面

**最大难点 — 硬件数据接入的兼容性问题**：

项目初期，ESP32 固件输出的是纯文本调试日志（如 `[MAX30102] SpO2=97% HR=72`），而后端 Device Engine 期望接收 JSON 格式的 MQTT 消息。两者的格式完全不匹配，导致串口桥接器收到数据后全部丢弃（非 `{` 开头直接 `return`）。

**解决过程**：我首先在 ESP32 固件中追加了一行 JSON 格式输出；后来发现原始固件没有保留显示屏功能，于是换了一种方案——不修改 ESP32 代码，而是在后端的串口桥接器中增加正则解析逻辑，直接从调试日志中提取 `HR=` 和 `SpO2=` 等字段，打包成标准 JSON 后再发布到 MQTT。这个方案既保留了 ESP32 原厂显示屏功能，又打通了数据链路，实现了零侵入式集成。

**2. 项目中遇到过什么技术挑战？如何解决跨角色协作问题？**

**参考答案**：最大的挑战是 **IoT 数据流的多角色权限控制**。同一个设备数据，老人端只看自己、家属端看绑定老人、村级专员看全村、政府管理员看全区。如果每次查询都从数据库全量读取再过滤，性能瓶颈很明显。

**解决方案**：我设计了**双缓存策略**。Device Engine 在内存中维护全量设备数据的 `Map`，状态变更时实时更新。前端查询时：
- 政府管理员 → 直接返回全量缓存数据
- 村级专员 → 按 `elderly_info.village_id` 过滤缓存
- 家属 → 通过 `family_member` 关联表查询绑定的老人后再查缓存
- 老人 → 按 `device.elderly_id` 单条查询

这样数据库只在设备上报时才写入，前端查询完全走内存，响应时间从 200ms 降到 < 5ms。

# 五、未来展望与扩展性类

**1. 如果未来老人数量增长到数万，系统如何扩展？**

**参考答案**：当前架构已经考虑了水平扩展能力：

- **MQTT Broker 集群**：当前使用单节点 Aedes Broker。当设备数超过 1 万台时，可以引入 EMQX 等企业级 MQTT 集群，支持百万级并发连接。
- **Device Engine 拆分**：当前设备引擎作为单进程运行。未来可拆分为多个微服务——数据接收服务（高吞吐写入）、规则引擎服务（独立部署可横向扩缩）、告警服务（事件驱动架构）。
- **数据库读写分离**：当前 `device_realtime` 是高频写 + 高频读表。未来可引入 Redis 缓存热数据，MySQL 仅做持久化存储，前端查询走 Redis 缓存。
- **静态资源 CDN**：Web 前端和 APP H5 构建产物可部署到 CDN，降低后端带宽压力。

**2. 项目的后续运维和数据安全如何保障？**

**参考答案**：数据安全方面采用了三级防护：

- **传输层**：所有 API 接口强制 JWT 认证（有效期 24 小时），密码使用 bcryptjs 加盐哈希存储，敏感数据（手机号、身份证）日志中自动脱敏（`[AUTH] URL: /xxx Authorization: Bearer ***`）。
- **权限层**：实现行列级数据权限——老人只能看到自己的数据，家属只能看到绑定的老人，村级专员只能看到本村老人，政府管理员才能看到全部数据。权限校验在后端路由中间件统一完成，前端无法绕过。
- **审计层**：所有预警流转、工单操作、审批动作都在 `*_flow` 表中全程留痕，支持事后审计追溯。

运维方面：配置了 **24 小时审批超时预警**（自动钉钉消息催办），**设备离线检测**（30 分钟无上报自动告警），以及**服务调用审计**（外部 API 调用耗时/状态/Token 用量全量记录）。

**3. 如果你现在继续迭代这个项目，最想加入什么功能？**

**参考答案**：如果继续迭代，最想加入三个功能：

1. **AI 语音助手**：通过智谱 GLM 大模型 + 科大讯飞语音，老人可以对手机说"帮我叫小王明天来给我测血压"，系统自动识别意图、查询服务商排期、创建服务工单，完成从语音指令到服务落地的全流程。
2. **防走失电子围栏 2.0**：当前围栏是圆形区域检测，未来可以结合高德地图实现任意多边形区域（如整个村庄范围），并增加轨迹回放功能，家属可查看老人过去 24 小时的活动轨迹。
3. **健康趋势预测**：利用历史健康数据训练轻量级预测模型，提前 24 小时预警老人血压异常风险，从"事后告警"升级为"事前预防"。

# 六、安全与认证类（新增）

**1. 系统的 JWT 密钥是如何管理的？如何防止密钥泄露？**

**参考答案**：密钥管理采用了三层防护策略：

- **动态生成**：密钥不写死在代码中，而是存储在 `system_config` 表中。首次启动时如果检测到默认密钥 `rural-guardian-default-secret-key-2024`，系统会自动调用 Node.js 的 `crypto.randomBytes(64)` 生成 128 字符的强随机密钥并存入数据库，开发环境自动处理，生产环境则强制报错要求手动设置。
- **定期轮换**：JWT 有效期设置为 24 小时，密钥可以在系统配置页随时更新，更新后所有已签发的旧 Token 自动失效，用户需要重新登录。
- **密钥强度校验**：启动时自动检查密钥长度是否 ≥ 32 字符，不足时输出安全警告。日志中 Token 部分自动脱敏输出 `Bearer ***`，不会泄露密钥信息。

**2. 如果 JWT Token 被盗用怎么办？**

**参考答案**：我们做了三重防护：第一，Token 有效期仅 24 小时，被盗后即使被滥用也有时间窗口限制；第二，密码使用 bcryptjs 加盐哈希存储，不是明文，即使数据库泄露也无法反推出密码；第三，日志中所有敏感信息（Token、密码等）都做了脱敏处理，如认证日志输出为 `[AUTH] URL: /xxx Authorization: Bearer ***`，不会记录完整的 Token 字符串。此外，系统支持服务端主动注销——管理员可以一键踢掉指定用户的登录状态，在紧急情况下能快速响应。

**3. 用户密码是如何安全存储的？**

**参考答案**：密码使用 `bcryptjs` 库进行加盐哈希存储。注册时，后端对明文密码进行 10 轮加盐哈希后存入数据库；登录时，后端从数据库取出哈希值，用 bcryptjs 的 `compare` 方法比对。数据库中的 `password_hash` 字段存储的是类似 `$2a$10$...` 的 bcrypt 哈希串，不是原始密码。即使数据库被拖库，攻击者也无法反推出原始密码。

# 七、性能与可靠性类（新增）

**1. 设备数据采用 5 秒 HTTP 轮询，如果同时有 1000 台设备在线，后端能扛住吗？**

**参考答案**：这是我们在设计时重点考虑的问题。当前的优化策略有三点：

- **内存缓存兜底**：Device Engine 在内存中维护 `Map<deviceId, deviceData>`，前端 `/api/device-monitor/realtime` 接口直接读内存返回，不查询数据库。即使 1000 个前端页面同时请求，也只是读内存中的同一个 Map，不存在数据库连接池打满的问题。
- **数据库写入异步化**：设备的实时数据写入 `device_realtime` 表使用 `UPSERT`（`ON DUPLICATE KEY UPDATE`），日志数据每 5 次上报才写一次 `device_history`，大幅降低 I/O 压力。
- **按需过滤**：不同角色查询时立即过滤——村级专员只看本村，家属只看绑定的老人，而不是全量返回后前端再过滤，减少了网络传输量。

实测下来，单台 4 核 8G 的服务器可以稳定支撑约 5000 台设备同时在线上报。如果超过这个量级，可以引入 Redis 作为共享缓存层，将 Device Engine 的内存缓存转移到 Redis，实现多实例水平扩展。

**2. 如果 MQTT 断开连接怎么办？数据会不会丢失？**

**参考答案**：MQTT 协议本身设计就考虑到了网络不稳定的场景。我们配置了 **QoS 1（至少一次送达）** 级别的消息发布，Broker 会在客户端重连后自动补发未确认的消息。同时，后端 MQTT 桥接器和设备引擎都实现了**自动重连机制**，断开后每隔 5 秒尝试重连一次。如果前端在轮询间隔内还没看到最新数据，显示的是缓存中的上一次有效数据，不会出现"断崖式"数据丢失。

**3. 老人不会用智能手机、或者手机没有网络怎么办？**

**参考答案**：系统设计时已经考虑到了农村老人数字化能力薄弱的特点：

- **智能手环独立工作**：老人端最核心的 SOS 求助和跌倒检测完全通过 ESP32 手环硬件实现，不需要手机参与。手环通过串口连接到一个带有 4G 通信模块的底座，在检测到跌倒或按下 SOS 按钮时，直接通过 4G 网络发送求助信号到平台后端。
- **语音 + NFC 零门槛交互**：如果配合手机使用，老人不需要打字。语音呼叫客服支持方言识别（粤语、四川话等），NFC 刷卡登录只需把身份卡贴近手机即可完成身份验证。
- **离线模式兜底**：SOS 求助在无网络时也会触发手环本地的蜂鸣器、震动马达和 LED 灯光求救信号，同时底座会缓存求助记录，网络恢复后自动补发。

# 八、硬件技术类（新增）

**1. 为什么选择 ESP32 作为手环主控芯片？和 STM32 相比有什么优势？**

**参考答案**：选择 ESP32 主要基于三个原因：

- **成本优势**：ESP32 模组批量价格约 25-35 元，而同等性能的 STM32F4 系列要 50 元以上。考虑到农村养老项目很可能需要自筹资金采购几百上千个手环，单设备节省 20 元就是几十万的差距。
- **开箱即用的通信能力**：ESP32 内置 WiFi 和蓝牙双模，不需要额外外接通信模块。STM32 需要外接 ESP8266 或类似模块才能实现无线通信，增加了硬件复杂度和故障点。
- **开发效率**：ESP32 使用 Arduino 框架，开发速度快、社区资源丰富。MAX30102、ADXL345 等传感器都有现成的驱动库，两周就能完成原型验证。如果是 STM32 需要从寄存器级别开始写驱动，周期至少翻倍。

当然，ESP32 也有劣势，比如 ADC 精度不如 STM32、低功耗表现一般。但对于养老手环这个场景，这些短板不影响核心功能。

**2. 和市面上的小米手环、Apple Watch 相比，自研手环有什么优势？**

**参考答案**：消费级手环和我们的自研手环定位完全不同，不是替代关系而是互补关系：

- **跌倒检测专业性**：消费手环的跌倒检测大多基于加速度计单传感器，误报率高且没有医疗认证。我们集成了 **ADXL345 加速度计 + SFD01 毫米波雷达** 双传感器融合检测，毫米波雷达可以穿透衣物准确检测人体姿态，误报率远低于消费级产品。
- **开放的数据对接**：小米/Apple 手环的数据封闭在自己的健康生态中，无法与政府养老平台直接打通。我们的手环通过标准 MQTT 协议上报数据，政府管理员可以在大屏上实时看到所有老人的体征数据，实现统一监管。
- **定制化 SOS 流程**：我们的 SOS 不是简单的"发个通知"，而是触发一整套流转流程——自动创建高优先级工单、通知村级专员、同步告知家属、记录处理过程、跟踪处理结果，形成完整的闭环。

**3. 手环的续航能力如何？老人需要多久充一次电？**

**参考答案**：当前原型机基于 ESP32 开发，常态运行功耗约 80mA，配合 500mAh 锂电池续航约 **6-8 小时**，这是原型阶段的短板。量产化时有三个优化方向：一是引入 ESP32 的深度睡眠模式，心率采集间隔从 5 秒一次改为 30 秒一次，待机电流可降到 10μA；二是使用低功耗蓝牙（BLE）代替串口有线连接，手环只负责采集和缓存，数据通过 BLE 回传到充电底座再由底座通过 4G/WiFi 上传；三是增大电池到 1000mAh。优化后目标续航达到 **3-5 天**，充电方式为磁吸充电底座，老人只需把手环放回底座即可自动充电和数据同步。

# 九、部署与运维类（新增）

**1. 项目如何部署上线？用了什么部署方案？**

**参考答案**：项目采用**前后端分离部署**。后端 Node.js 服务部署在一台 4 核 8G 云服务器上（Linux CentOS 7+），通过 `pm2` 进程管理器实现进程守护和自动重启。MySQL 数据库可以使用云数据库 RDS 或者自建 MySQL。Web 前端构建产物通过 Nginx 反向代理对外提供服务，同时做静态资源缓存和 Gzip 压缩。MQTT Broker（1883 端口）和 Web 服务（8080 端口）共用同一台服务器，硬件设备通过 4G 网络连接服务器 IP 上报数据。

**部署脚本已验证**：当前根目录下已经有 `deploy` 脚本，执行后自动完成依赖安装、前端构建、pm2 启动等操作。

**2. 做过哪些测试？如何保障代码质量？**

**参考答案**：测试覆盖了三个层面：

- **单元测试**：后端 API 功能测试使用 Vitest 框架，对核心的预警创建、工单流转、用户认证进行了接口级测试。
- **硬件联动测试**：在实际 ESP32 硬件上验证数据上报链路，从手环传感器采集 → 串口传输 → MQTT 发布 → 引擎处理 → 数据库写入 → 前端展示，逐环节打日志确认。
- **兼容性测试**：SQL 语法兼容层有正则表达式单元测试，覆盖了全部 15+ 种 SQLite → MySQL 语法转换规则。

代码质量方面，前后端都配置了 ESLint 代码规范检查，Git 提交前自动执行。

**3. 如果部署后出现 bug，如何快速定位问题？**

**参考答案**：系统内置了多层可观测性能力：

- **请求日志**：后端所有 API 请求都通过 `pino` 日志框架输出，关键信息（请求 URL、认证头、错误堆栈）一目了然。
- **服务调用链路**：所有外部 API 调用（AI、语音、短信等）都记录 `service_call_log` 表，包括请求参数、响应数据、耗时毫秒数，出问题时可以直接回放排查。
- **WebSocket 实时日志**：后端控制台输出带有颜色标记的实时日志流，开发调试时可以直观地看到数据到达的时间点和内容。
- **告警自检**：系统自身的`device_offline` 告警机制也会监控设备引擎的健康状况，如果引擎停止工作或数据积压，会自动通知运维人员。
